# Customer documents

Approved customer-document template for future companies. The existing internal proposal and research exports are unchanged.

After reviewing the analysis, an authorized room member selects **Create customer document** from the company overview or proposal page. They choose an assessment (no prices) or a proposal, review the analysis text, add direction, and explicitly approve that input for drafting. Unresolved chief findings require a direction note. Priced customer proposals require the existing pricing review to be ready/passed and all items priced; held estimates are never used.

Gemini writes customer prose through the existing server-side provider. Financial amounts are computed from saved proposal items in code, never generated by the model. Customer documents are separate snapshots in `state.customer_documents`, with input approval actor/time/text, source digest, provider usage, and output approval actor/time. Creation is manual only; the research worker never invokes it. A maximum of 12 documents bounds storage. Existing room membership, lock checks, optimistic versions and RLS apply. No new database schema is required.

Draft Word/PDF downloads are marked as drafts. The full customer text can be edited before approval. Saving edits clears approval. Approval requires a second explicit confirmation and a matching digest of the underlying analysis, proposal, review, verification, notes and decisions. Source changes block approval and approved downloads; create a fresh draft to use new evidence. Approval is an internal release decision, not customer acceptance, a sales-stage change, or a send action.

The StyleBAR-inspired design uses Sweetwater branding, dark headings, blue section labels, readable spacing, clear recommendations, existing improvements versus optional work, evidence limits and customer-owned handoff. Export uses an explicit field allowlist, never room notes, agent transcripts or internal estimating metadata. Human reviewers still must check generated prose and source claims; structured JSON is not a factual guarantee.

## Full assessment standard (November 10, 2026)

The initial short-summary design was rejected in review. Customer documents now use an eight-part editorial model shared by Word and PDF: recommendation/outcome/strengths; two work tracks and priorities; detailed evidence-linked findings; illustrative customer journeys; discovery; bounded delivery; handoff and success checks; sources and limitations. The model allows overflow without clipping, so eight sections do not guarantee eight pages for every company. The ACA example is about 2,600 words and eight pages in each format. Its copy is curated from saved evidence, not a new live audit or a live Gemini generation.

`CUSTOMER_ASSESSMENT_STANDARD` defines section-specific drafting instructions. New template-version-2 documents require the expanded sections and findings with Evidence, Why it matters, Recommended response and Completion check. The same validation applies when saving/approving version-2 drafts. Older drafts remain readable. Completeness checks do not certify factual accuracy or prose quality; Clint and Sheree remain the approval gate. The 14,000-token customer-document budget reserves output room with LOW Gemini 3 thinking and retains incomplete-output rejection. Oversized evidence packets fail explicitly rather than silently truncating.

Sweetwater's logo is extracted from the supplied StyleBAR reference and embedded in `customerDocumentBrand.mjs`; no remote logo dependency is used. The new customer-only renderers leave existing research/proposal exports unchanged. Shared editorial structure ensures all allowlisted customer fields and deterministic pricing appear in both formats. The example preserves the office/field-phone distinction, dated and separate Google samples, the observed sitemap, blocked Instagram checks and unresolved namesake account ownership. No live proposal or room data was changed.

Validation: 108 Project Room tests; 10 provider tests; TypeScript and backend type checks; browser creation/approval/edit reset and Word/PDF downloads on desktop/mobile with no page errors. Word was rendered using a hidden, read-only Microsoft Word conversion because the packaged LibreOffice renderer is unavailable on this Windows runtime; rendered pages and the app's separate PDF export were inspected. An outdated existing provider test assumed six chief checks; it now asserts the six core checks plus all five local-presence checks.

Lesson: a visual reference defines information depth and editorial structure as well as colors. Validate the document's substance and every rendered page before calling a template matched.
